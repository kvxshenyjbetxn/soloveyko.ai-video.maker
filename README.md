# Soloveyko.ai Video Maker

Десктопна програма для автоматизованого створення відео: переклад сценарію, озвучка, генерація відеоряду, субтитри та монтаж — все в одному пайплайні. Побудована на Rust + egui, кросплатформена (Windows / macOS).

---

## Архітектура

**Стек:** Rust + [eframe](https://github.com/emilk/egui/tree/master/crates/eframe) (egui). Один головний потік UI, всі мережеві запити або системні процеси (наприклад, виклики Claude CLI чи Gemini CLI) виконуються у окремих `std::thread::spawn` потоках та повертають результат через `Arc<Mutex<Option<T>>>` + `ctx.request_repaint()`. Для обмеження паралельних запитів до API OpenRouter, запусків Claude CLI, Gemini CLI та з'єднань до Edge TTS використовуються потокобезпечні глобальні лімітери (семафори), що запобігають перевищенню лімітів та перевантаженню системи.

**State management:** Весь стан програми живе у єдиній структурі `VideoMakerApp` (`src/app.rs`). Немає глобальних змінних. Налаштування автоматично персистяться у JSON-файл при кожній зміні (але тільки коли миша відпущена — щоб не бомбардувати диск під час перетягування бічної панелі).

**Два режими відображення:** вкладка `Main` (редактор + панель пайплайну) та вкладка `Settings` (тема, мова, колір акценту).

**Розділення відповідальностей:**
- `api/` — тонкі обгортки для зовнішніх сервісів (перевірка балансу, ключів, робота з TTS)
- `core/pipeline/` — бізнес-логіка кожного етапу пайплайну (HTTP виклик + збереження файлу + статус задачі)
- `gui/pipeline/` — тільки UI-компоненти панелі пайплайну

## Ключові компоненти

### `VideoMakerApp` (`src/app.rs`)

Центральна структура. Реалізує `eframe::App`, тобто метод `update()` — головний loop рендерингу.

- **Форма швидкого збереження шаблонів у заголовку:** Замість колишнього статичного заголовку "Налаштування пайплайну", у самому верху бічної панелі інтегровано зручну форму швидкого збереження поточних налаштувань у шаблон (текстове поле вводу назви + кнопка "Зберегти"). Це значно економить корисний простір інтерфейсу.
- **Баланс-чіпи в топбарі та налаштування лімітів:** при кліку на будь-який чіп відкривається вікно `draw_balance_window`. Чіпи відображаються тільки якщо баланс вже завантажений (не `None`). VoiceBot показує лише перше слово балансу (числове значення), щоб не займати місце. Секція Edge TTS безкоштовна, тому відображає статус "Безкоштовно (Без лімітів)". Секція VoiceBot відображає інформацію про фіксоване обмеження в 5 паралельних потоків. У цьому ж вікні інтегровано повзунки `egui::Slider` (від 1 до 25) для регулювання `openrouter_max_threads`, `claude_max_threads`, `gemini_max_threads` та `edge_tts_max_threads`. Будь-яка зміна цих повзунків миттєво оновлює відповідні глобальні лімітери запитів та автозберігається на диск. Повзунки для Googler (`googler_image_max_threads` та `googler_video_max_threads`) вбудовані безпосередньо в рядки "Потоки зображень" та "Потоки відео" у гриді балансу Googler — поруч з поточним числом активних потоків. Чіп Googler в топбарі також відображає ці локальні ліміти (а не серверне `threads_allowed`).
- **Динамічний статус етапів у картках задач черги:** Біля назви кожного етапу у дужках виводиться кількість токенів та символів тексту:
  - Для етапів **Переклад** та **Оригінал** завжди виводиться статистика оригінального тексту.
  - Для етапу **Озвучка**: якщо переклад вимкнено — виводиться статистика оригінального тексту. Якщо переклад увімкнено — до завершення перекладу відображається статус `(очікує перекладу)`.
  - Після успішного завершення етапу перекладу дані етапів **Переклад** та **Озвучка** динамічно перемикаються на реальну кількість токенів та символів вже **перекладеного** тексту.
- **Відображення витрат OpenRouter:** Якщо переклад здійснюється через сервіс OpenRouter, після його завершення у дужках біля етапу «Переклад» автоматично з'являється точна вартість запиту в доларах (наприклад, `$0.00015`), отримана безпосередньо з API.
- **Автозбереження:** в кінці `update()` порівнюється поточний стан з `last_saved_settings`. Якщо щось змінилось і миша відпущена (`!pointer.any_down()`) — файл перезаписується. Дельта для `translation_temperature`: > 0.001 (щоб уникнути зайвих записів під час перетягування повзунка).
- **Баланси завантажуються при старті:** якщо в налаштуваннях вже є ключі — виклик `fetch_balance` відбувається в `VideoMakerApp::new()`. OpenRouter перевіряється тільки якщо ключ починається з `sk-or-`.
- **Ініціалізація та зворотна сумісність моделей перекладу:** при старті програми (`load_settings`) та завантаженні шаблонів виконується розумний fallback. Якщо нові індивідуальні поля моделей для сервісів порожні, програма переносить значення зі старого спільного поля `translation_model` у правильний слот поточного активного сервісу та ініціалізує інші слоти дефолтами (наприклад, `"sonnet"` для Claude та `"gemini-2.5-flash"` для Gemini).
- **Ширина панелі пайплайну:** egui зберігає ширину через `egui::Memory` між сесіями автоматично. `default_width` передається лише при першому запуску програми — далі егуі управляє шириною сам.
- **Нижня панель черги та ресайз:** `TopBottomPanel::bottom("queue_panel")` рендериться після правої бічної панелі пайплайну, тому вона візуально обмежується нею та не заходить під неї. Вона підтримує вертикальний ресайз `.resizable(true)` з межами висоти від 75px (мінімум) до 350px (максимум) з дефолтним значенням 90px. При збільшенні висоти картки адаптивно розширюються по вертикалі, показуючи більші іконки та деталі.
- **Клікабельність задач та вікно логів:** Кожна картка в черзі є інтерактивною (`Sense::click()`). При наведенні курсор змінюється на `PointingHand`. Клік по картці встановлює стан `selected_job_logs` та відкриває окреме спливаюче вікно `egui::Window` з детальними логами виключно цієї задачі.
- **Клікабельність задач та вікно контролю перекладу:** Якщо задача перебуває у статусі `AwaitingControl` (Очікує контролю), клік по її картці у черзі відкриває спеціальне вікно «Контроль перекладу» з текстовим полем та кнопкою «Підтвердити та продовжити». Це дозволяє перевірити та відредагувати отриманий переклад на льоту перед запуском наступних етапів. Між текстовим полем та кнопками відображається рядок статистики перекладеного тексту (символи • слова • токени) — оновлюється в реальному часі під час редагування. Якщо переклад виконувався через OpenRouter, поруч зі статистикою додатково відображається точна вартість запиту у форматі `$0.00000`.
- **`job_name_dialog_open` / `job_name_input`** — стан діалогового вікна назви задачі. Ephemeral, не зберігається у `settings.json`.

### Текстовий редактор сценарію (`src/gui/editor.rs`)

Центральна панель програми з безрамковим редактором сценарію (`frame(false)`), що забезпечує ефект "чистого аркуша" на всю высоту робочої області.

- **Динамічний підрахунок токенів:** Інтегровано pure-Rust бібліотеку `tiktoken` із кодуванням `cl100k_base` (стандарт для GPT-4, Claude тощо). Підрахунок працює миттєво при кожній зміні тексту та однаково точно рахує як латиницю, так і кирилицю.
- **Оптимізована продуктивність:** Для виключення зайвих алокацій під час рендерингу (update loop), функція `get_encoder()` повертає статичне посилання `&'static CoreBpe` безпосередньо з бібліотеки `tiktoken`, яка кешує словник під капотом.
- **100% автономність (Offline-first):** BPE-таблиці токенізатора повністю вбудовані в бінарний файл програми при компіляції. Розрахунок виконується повністю локально без мережевих запитів.

### Черга задач (`src/queue.rs`)

- **`JobSettings`** — знімок усіх налаштувань пайплайну на момент додавання задачі. Зберігається в `PipelineJob` для можливого майбутнього перезапуску. Додаткові поля: `translation_control_enabled`, `voiceover_enabled`, `voicebot_key`, `voiceover_template_uuid`, `voiceover_provider`, `edge_tts_voice`, `edge_tts_rate`, `edge_tts_pitch`, `edge_tts_volume`.
- **`JobStatus`** — `Pending → Running / AwaitingControl (пауза для контролю перекладу) → Done / Failed(String)`. Обгорнутий у `Arc<Mutex<T>>`, бо змінюється з фонового потоку.
- **`translated_text` та `translation_cost`** — додаткові потокобезпечні поля в `PipelineJob`, які служать для надійного кешування результату перекладу сценарію та його фактичної вартості безпосередньо в оперативній пам'яті програми.
- **`StageStatus`** — `Pending / Running / Done / Failed` (без деталей помилки). Кожен `PipelineJob` має два окремих поля: `translation_stage` та `voiceover_stage`. Слугують виключно для UI: картка задачі фарбує назву кожного етапу відповідним кольором (сірий / жовтий / зелений / червоний).
- **`PipelineJob::name`** — назва задачі, яку вводит користувач у діалозі. Якщо поле пусте — автоматично генерується як "Задача N" (де N = `jobs.len() + 1` на момент додавання).
- **Двоетапний workflow:** додавання задачі (`Pending`) і запуск (`Running`) — два окремі дії. Користувач може накопичити кілька задач у черзі і потім запустити їх усі кнопкою "▶ Запустити".

### Панель пайплайну (`src/gui/pipeline/mod.rs`)

Права бічна панель з 9 секціями у порядку: Шаблони → Шлях збереження → АПІ → Контроль → Переклад → Озвучка → Відеоряд → Субтитри → Монтаж.

- **Ідеальне вирівнювання заголовків та розділювачів:** Ліва панель статистики сценарію (`src/gui/editor.rs`) та права бічна панель пайплайну мають ідентичні заголовки з великим шрифтом `16.0`. Їхні лінії-розділювачі вирівняні ідеально по горизонталі (на одній висоті `y`). Самі заголовки візуально відцентровані по вертикалі за допомогою точно збалансованих асиметричних відступів (`8.0` зверху та `4.0` знизу).
- **Дизайн розділювачів "border-to-border":** Контейнери обох панелей (`CentralPanel` та `SidePanel`) мають нульові внутрішні відступи, завдяки чому горизонтальні лінії-розділювачі йдуть від лівого до правого краю без проміжків. Всі внутрішні елементи та секції налаштувань загорнуті у фрейми з бічними відступами `8.0` пікселів, що запобігає прилипанню елементів керування до країв екрана.
- **Секція "Шлях збереження" прихована за замовчуванням:** Для створення лаконічного, незахаращеного та охайного інтерфейсу при першому запуску програми, секція вибору шляху збереження завантажується у згорнутому стані.
- **Два шляхи збереження (macOS / Windows):** Секція показує два окремих поля — одне для macOS, інше для Windows. Активна платформа підсвічується мітками `(активний)`. При запуску `effective_save_path()` автоматично обирає потрібне поле через `cfg!(target_os = "macos")`. Це дозволяє переносити `settings.json` між ПК на різних ОС без ручного виправлення шляхів.
- **Секції "Переклад", "Озвучка", "Відеоряд", "Субтитри", "Монтаж"** мають toggle-перемикач (`toggle_switch`) прямо в заголовку. Стан перемикача відображається плавною анімацією через `animate_bool_responsive`.
- **Кнопка швидкої вставки плейсхолдера `{{text}}`** у секції «Переклад» розміщена під текстовим полем промту і для лаконічності підписана просто як `{{text}}`. Під кнопкою відображається коротка підказка-пояснення: `{{text}} - місце куди встане текст перекладу.` для спрощення користувацького досвіду (UX). При натисканні на кнопку плейсхолдер безпечно вставляється у байтову UTF-8 позицію рядка за поточним положенням курсора без втрати фокусу.
- **Форма шаблону** завжди видима поза `ScrollArea` — навмисно, щоб не ховалась при скролі. Кнопка "Додати в чергу" також зафіксована внизу панелі.
- **ScrollArea обмежена по висоті** (`max_height = available_height - bottom_reserve`) — щоб залишити місце для кнопки та помилки внизу.
- **Всі секції** реалізовані через `CollapsingState` з persist id — egui запам'ятовує чи розкрита секція між кадрами.
- **Кнопка "Додати в чергу":** спочатку валідує поля (текст, шлях, модель, ключ). Якщо все ок — відкриває `egui::Window` з полем для введення назви задачі. Вікно по центру екрана, підтримує `Enter` для підтвердження.
- **`validate_and_enqueue`** — більше НЕ запускає обробку. Тільки створює папку `{save_path}/{task_name}/` через `std::fs::create_dir_all` і додає `PipelineJob` зі статусом `Pending`. Реальний запуск — через кнопку "▶ Запустити" в панелі черги.

### Пайплайн виконання задачі (`src/core/pipeline/`)

**`run_pipeline`** (`mod.rs`) — єдина точка запуску задачі. Spawns один потік, виконує послідовно всі увімкнені етапи у межах цього потоку. Статус задачі: `Pending → Running → Done / Failed`.

#### Переклад (`translate/`)

- **`translate_text`** (`mod.rs`) — синхронна функція: будує `user_content` з промту + тексту, викликає відповідний сервіс. Повертає `Result<(String, Option<f64>), String>`, що включає перекладений текст та його вартість (для OpenRouter). Не знає нічого про статуси, файли чи потоки.
- **`call_openrouter`** (`translate.rs`) — чистий HTTP виклик до OpenRouter Chat completions API. Повертає текст відповіді та її вартість (отриману безпосередньо з поля `usage.cost` у відповіді API, що гарантує 100% точний та миттєвий облік витрат).
- **Плейсхолдер `{{text}}`:** якщо промт містить `{{text}}` — текст підставляється на місце. Якщо промт є але без плейсхолдера — текст додається після промту через `\n\n`. Якщо промт порожній — надсилається тільки текст.
- При успіху зберігає результат у `{save_path}/text.txt`. Цей же текст передається в озвучку якщо вона увімкнена.
- **Контроль перекладу (Translation Control):** Якщо увімкнено відповідне налаштування у секції "Контроль", то після завершення перекладу задача призупиняється. Її статус змінюється на `Очікує контролю` (AwaitingControl), а фоновий потік завершує роботу. Клік по картці такої задачі відкриває вікно "Контроль перекладу", де користувач може перевірити та відредагувати текст. При натисканні "Підтвердити та продовжити" оновлений текст зберігається, а пайплайн перезапускається відразу з наступного кроку (Озвучки), використовуючи відредагований варіант.

#### Озвучка (`voiceover/`)

**`run_voiceover_sync`** (`voiceover/voiceover.rs`) — синхронна функція, викликається з `run_pipeline` після перекладу (або замість нього, якщо переклад вимкнено). Підтримує двох провайдерів:
1. **Voice Bot** — виконує запити до стороннього API VoiceBot із циклічним опитуванням (polling) статусу готовності задачі. Перед кожним запитом потік отримує дозвіл у глобального лімітера `VoiceBotLimiter`, що обмежує кількість паралельних з'єднань до 5.
2. **Edge TTS** — використовує вбудовану стабільну бібліотеку `msedge-tts` (версія 0.4.0) для миттєвого та безкоштовного перетворення тексту на мовлення без лімітів та DRM-проблем.

**Логіка Edge TTS:**
- **Спрощення імен голосів:** Довгі системні назви голосів від Microsoft Edge TTS (наприклад, `Microsoft Dmitry Online (Natural) - Russian (Russia)`) автоматично скорочуються функцією `clean_friendly_name` в `src/api/edgetts.rs` до лаконічного та зрозумілого формату `Dmitry (Russian, ru-RU)`. Це робить інтерфейс ComboBox чистим та читабельним.
- **Інтерактивні повзунки (Sliders):** Параметри темпу (`rate`), тональності (`pitch`) та гучності (`volume`) тепер регулюються за допомогою зручних повзунків `egui::Slider` у межах від `-100` до `100`. Повзунки мають відповідні суфікси `%` та `Hz` для зручності візуального сприйняття та плавного налаштування.
- **Розбиття на чанки:** Реалізовано інтелектуальний алгоритм `split_text_by_chunks`, який розбиває довгі сценарії на окремі чанки розміром до **6000 символів**, зберігаючи цілісність слів та абзаців.
- **Паралельна генерація:** Чанки надсилаються до Edge TTS паралельно у фонових потоках (`std::thread::spawn`). Кожен потік перед з'єднанням отримує дозвіл у глобального лімітера `EdgeTTSLimiter`, що регулює навантаження.
- **Повторні спроби (Retries):** У разі збою мережі потік автоматично робить до 3 спроб із експоненціальною затримкою (`5s`, `10s`, `15s`).
- **Склеювання (Merging):**
  1. *Основний шлях:* Аудіофайли чанків об'єднуються за допомогою системного виклику `FFmpeg` (concat demuxer без перекодування, що дає миттєвий результат без втрати якості).
  2. *Fallback шлях:* Якщо `FFmpeg` не знайдено в системі, програма виконує пряме бінарне склеювання MP3-байтів у вихідний файл `voice.mp3`. Це гарантує 100% безвідмовну роботу на будь-якому комп'ютері.

**Джерело тексту:** якщо переклад увімкнено — озвучується перекладений текст. Якщо переклад вимкнено — оригінальний текст (`settings.text`). Картка задачі показує це окремим рядком: "Переклад" (кольоровий за статусом) або "Оригінал" (завжди зелений, бо текст уже є).

### Вікно привітання (`src/gui/welcome.rs`)

З'являється при першому запуску (або якщо `show_welcome: true` у `settings.json`). Перевіряє наявність трьох CLI-інструментів асинхронно у фонових потоках, одразу при ініціалізації `VideoMakerApp::new()`.

- **`ToolStatus`** — три стани: `Checking` / `Installed(String)` / `NotInstalled`. Зберігається в `Arc<Mutex<ToolStatus>>`.
- **`ToolChecks::start()`** spawns три окремих `std::thread::spawn`. Кожен запускає відповідну команду (`npm --version`, `gemini --version`, `claude --version`) та оновлює статус після завершення через `ctx.request_repaint()`.
- **На Windows** перевірки запускаються через `cmd /C <name> --version` (аналогічно до `api/gemini.rs` та `api/claude.rs`).
- **Команди встановлення** показуються тільки якщо інструмент `NotInstalled`, залежать від OS: Mac — `brew install node` / `sudo npm install -g @google/gemini-cli`, Windows — `winget install OpenJS.NodeJS` / `npm install -g @google/gemini-cli`. Claude Code орієнтований на npm для всіх систем.
- **"Не показувати":** галочка `dont_show` + кнопка "Зрозуміло". `draw_welcome_dialog` повертає `true` лише коли кнопку натиснуто. Якщо `closed && dont_show` — `app.rs` миттєво зберігає `show_welcome: false` через явний виклик `save_settings` (не через автозбереження), щоб не гратися з `last_saved_settings`.
- **Повернення вікна через Налаштування:** вкладка `Settings` → секція "Привітальне вікно" містить галочку `show_welcome`. При її зміні `draw_settings` повертає `bool`, і `app.rs` одразу викликає `save_settings` з актуальними `last_saved_settings`. Вікно з'явиться при наступному запуску програми.
- **Фонова перевірка при виборі сервісу:** якщо користувач обирає `"Gemini CLI"` чи `"Claude Code"` як сервіс перекладу, автоматично запускається фонова перевірка. Для цього використовується поле `pending_tool_check` у `VideoMakerApp`. Коли перевірка завершується, якщо потрібний інструмент не встановлений (`NotInstalled` для `claude` або `npm`/`gemini`), програма автоматично відкриває привітальне вікно (`welcome_open = true`) з детальним статусом та інструкціями для встановлення.

### Збереження налаштувань (`src/gui/settings/storage.rs`)

Два JSON-файли зберігаються у `<UserConfigDir>/Soloveyko.AI-Video.Maker/`:
- `settings.json` — `AppSettings`: весь стан програми (тема, ключі, ширина панелі, стан пайплайну, індивідуальні налаштування Edge TTS, `googler_image_max_threads`, `googler_video_max_threads`).
- `templates/<name>.json` — `PipelineTemplate`: набір налаштувань пайплайну для швидкого перемикання між конфігами. Включає поля `googler_image_max_threads` та `googler_video_max_threads` — при завантаженні шаблону вони відновлюються разом з усіма іншими налаштуваннями.

`AppSettings` та `PipelineTemplate` мають `#[serde(default)]`, тому старі файли без нових полів не ламаються (дефолт для нових полів потоків Googler — `5`). Поле `show_welcome` має `default_true`, тому після оновлення на нову версію вікно привітання покаже себе один раз.

**Міграція `save_path`:** Старе єдине поле `save_path` у JSON замінено на `save_path_macos` / `save_path_windows`. При `load_settings`, якщо обидва нових поля порожні, але старий `save_path` непорожній — його значення автоматично переноситься у поле поточної платформи. Старий `save_path` не записується назад у JSON (`#[serde(skip_serializing)]`).

### API-сервіси (`src/api/`)

Тільки утилітарні запити (баланс, перевірка ключа, TTS). Всі запити — синхронні `ureq` або WebSocket-з'єднання, загорнуті в `std::thread::spawn`. Результат пишеться у `Arc<Mutex<Option<T>>>`, після чого `ctx.request_repaint()` ініціює перемальовування UI.

- **Глобальне лімітування запитів OpenRouter (`OpenRouterLimiter`), Claude Code (`ClaudeLimiter`), Gemini CLI (`GeminiLimiter`), Edge TTS (`EdgeTTSLimiter`) та VoiceBot (`VoiceBotLimiter`):**
  Потокобезпечні лімітери (семафори на базі `Mutex` та `Condvar` зі стандартної бібліотеки Rust) обмежують кількість одночасних запитів та паралельних запусків по всій програмі.
  - Метод `acquire()` блокує потік, якщо досягнуто ліміту активних запитів, повертаючи відповідний дозвіл-перміт (`OpenRouterPermit<'a>`, `ClaudePermit<'a>`, `GeminiPermit<'a>`, `EdgeTTSPermit<'a>` або `VoiceBotPermit<'a>`).
  - Завдяки реалізації трейту `Drop` для дозволів, ліміт автоматично звільняється (викликається `release()`) при виході з області видимості.
  - Лімітер OpenRouter інтегрований у перевірку балансу, переклад сценарію та фонове завантаження моделей. Лімітери Claude Code та Gemini CLI — у функції виклику відповідних CLI. Лімітер Edge TTS обмежує кількість паралельних фонових WebSocket-з'єднань при синтезі великої кількості чанків тексту. Лімітер VoiceBot обмежує кількість одночасних активних задач озвучки на сервері (фіксовано 5).

| Сервіс | Метод / Ендпоінт | Що робить / повертає |
|---|---|---|
| **OpenRouter** | `openrouter.ai/api/v1/credits` | Залишок кредитів: `$X.XX` |
| **VoiceBot (баланс)** | `voiceapi.csv666.ru/balance` | `balance_text` — рядок з кількістю символів |
| **VoiceBot (TTS)** | `POST /tasks` → `GET /tasks/{id}/status` | TTS: створення задачі → polling статусу → скачування MP3/ZIP |
| **Edge TTS (voices)** | `msedge_tts::voice::get_voices_list` | Завантажує повний список нейромережевих голосів Microsoft Edge |
| **Edge TTS (TTS)** | `msedge_tts::tts::client::connect` | Підключається та синтезує текст у MP3-байти за один запит |
| **Googler** | `googler.fast-gen.ai/api/v3/account/usage` | `GooglerBalance`: img/video used+limit, threads active+allowed |

**VoiceBot TTS статуси:** `waiting` → `processing` → `ending` (скачуємо) → `ending_processed`. При `error` / `error_handled` — кошти повертаються на баланс автоматично. Ліміт: 5 одночасних задач.

**НО — Googler `account_limits`:** поля лімітів могут бути або числом, або об'єктом з ключем `used`/`count`/`current_usage`. Функція `extract_i64()` обробляє обидва формати, бо API Googler непостійний у структурі відповіді.

### Глобальний логер та Вкладка Логів (`src/logger.rs`)

Система надає преміальний вбудований термінал логів для діагностики виконання завдань (зокрема запусків Claude CLI, Gemini CLI та з'єднань Edge TTS):
- **Потокобезпечний структурований логер:** реалізований на базі глобального `OnceLock<Mutex<Vec<LogEntry>>>` з обмеженням розміру до 1000 записів. Записує логи одночасно в інтерфейс додатку та в консоль розробника (`stdout`).
- **Прив'язка логів до задач:** Кожен запис `LogEntry` може містити `job_id` та `job_name`. Функція `log_job(job_id, job_name, msg)` записує лог із прив'язкою до задачі. У загальному списку такі логи автоматично маркуються префіксом `[Задача #ID: Назва]`.
- **Фільтрація логів:** Функція `get_job_logs(job_id)` дозволяє отримати логи тільки для конкретної задачі, що використовується у спливаючому вікні при кліку на картку задачі в черзі.
- **Часові мітки без важких залежностей:** для форматування часу `[HH:MM:SS]` використовується `std::time::SystemTime` та `UNIX_EPOCH` замість важкої сторонньої бібліотеки `chrono`.
- **Вкладка «Лог» (Logs):** відображається відразу після «Налаштування». Має стильний темно-вугільний вигляд з інтелектуальним підсвічуванням подій (червоний для помилок та stdout/stderr, зелений для успіхів, блакитний для команд, тьмяно-сірий для часу).
- **Керування логом та копіювання по кліку**: Увесь рядок логу є інтерактивним. Користувач може клікнути на будь-який рядок для його миттєвого копіювання до буфера обміну (візуальна підказка з'являється при наведенні). Також доступна кнопка «Очистити лог» (з червоним акцентом) та кнопка копіювання всього логу в буфер обміну.
- **Синхронізована автопрокрутка логів**: Чекбокси `"Автопрокрутка"` у загальній вкладці логів та в діалоговому вікні логів завдання дозволяють користувачам вільно переглядати старі записи без зсуву екрана при надходженні нових записів логів. Вони синхронізують спільний стан `auto_scroll_logs` додатку.
- **Преміальний Toast та термінальний стиль для завдань**: При копіюванні у правому нижньому кутку рендериться красивий `egui::Area` Toast, який за допомогою `ctx.request_repaint()` плавно відраховує 2 секунди та зникає. Діалогове вікно логів завдання тепер стилізовано під темно-вугільний термінал з повним розфарбовуванням статусів та копіюванням по кліку.

## Важливі нюанси та НО

- **Ініціалізація `rustls` `CryptoProvider`:**
  Через те, що в процесі одночасно скомпільовані два TLS криптопровайдери (`aws-lc-rs` від `ureq v3` та `ring` від `tungstenite`), бібліотека `rustls v0.23` вимагає явно встановити глобальний провайдер за замовчуванням. Ми додали пряму залежність `rustls` з фічею `ring` в `Cargo.toml` і викликаємо `let _ = rustls::crypto::ring::default_provider().install_default();` на початку `fetch_voices` та `synthesize`. Це запобігає паніці та гарантує стабільну роботу мережі на macOS та Windows.

- **Блокування на рівні лімітерів не впливає на GUI-потік.** Оскільки всі мережеві виклики та виклики CLI, захищені лімітерами, виконуються у фонових потоках (`std::thread::spawn`), будь-яке очікування вільного слоту відбувається непомітно для користувача і не спричиняє фризів інтерфейсу.

- **`googler_key` не входить у `PipelineTemplate`.** Ключ Googler зберігається тільки в `AppSettings` (глобальні налаштування), а не в шаблонах пайплайну. OpenRouter ключ — входить у шаблон. Така асиметрія є свідомою: шаблон — це конфіг пайплайну, а не конфіг акаунту.

- **Повзунки лімітів (`openrouter_max_threads`, `claude_max_threads`, `gemini_max_threads`, `edge_tts_max_threads`) не входять у `PipelineTemplate`.** Ці значення є системними і зберігаються лише в `AppSettings`. Натомість `googler_image_max_threads` та `googler_video_max_threads` **входять** у `PipelineTemplate` — бо ці ліміти безпосередньо впливають на поведінку пайплайну генерації медіа.

- **Баланс-чіп VoiceBot** показує лише перше слово (число) з `balance_text`, щоб не займати місце в топбарі. Повний текст видно у вікні балансів.

- **Googler-баланс у топбарі** відображає 8 значень в одному рядку (`img: X/Y vid: X/Y th: X/Y X/Y`). Перше `/Y` для потоків — це значення `googler_image_max_threads` зі стану програми (локальний ліміт, який задає сам користувач), а не серверне `threads_allowed`. Аналогічно для відео. Це зроблено свідомо, щоб чіп показував актуальні робочі ліміти а не серверні максимуми.

- **Повзунки Googler у вікні балансів вбудовані в Grid.** Повзунки `egui::Slider` для `googler_image_max_threads` та `googler_video_max_threads` відображаються прямо в рядках "Потоки зображень" та "Потоки відео" у Grid-таблиці поруч з числом активних потоків. Якщо баланс ще не завантажено — рендерується окрема таблиця `googler_threads_offline_grid` з `0 / slider` щоб користувач міг налаштувати ліміти навіть без підключення.

- **`windows_subsystem = "windows"`** у `main.rs` — приховує консоль у release-білді на Windows. У debug-режимі консоль є.

- **egui перемальовує весь фрейм щоразу** — тому будь-яка зміна стану одразу видна.

- **`translation_model_search`** — ephemeral-стан (рядок пошуку у дропдауні), не зберігається у `settings.json` та не входить у шаблон.

- **Повзунок температури (`translation_temperature`)** — перед рендерингом зчитується `ui.available_width()` і тимчасово переписує стиль повзунка в межах `scope`, щоб Slider не розтягував SidePanel.

- **Ширина елементів у `ui.horizontal()`:** egui додає `item_spacing.x` між кожною парою елементів. При розрахунку ширини треба відіймати саме `ui.spacing().item_spacing.x` — інакше SidePanel розповзається.

- **Секції "Субтитри" та "Монтаж"** поки порожні (заглушки).

- **Шлях збереження задачі** — не сам `save_path`, а `{effective_save_path}/{task_name}/`. `effective_save_path()` повертає `save_path_macos` або `save_path_windows` залежно від поточної ОС. Папка створюється при додаванні задачі в чергу (в `validate_and_enqueue`). Якщо `create_dir_all` падає — задача не додається, показується помилка.

- **Кольорова система статусів у картці задачі:** кожен увімкнений етап відображається окремим рядком і фарбується незалежно: сірий = очікує, жовтий = виконується, зелений = готово, червоний = помилка. "Оригінал" завжди зелений.

- **Архітектура пайплайну — один потік на задачу.** `run_pipeline` spawns один потік і послідовно виконує всі увімкнені етапи. Це гарантує правильну послідовність (переклад → озвучка, а не паралельно).

- **Файл озвучки `voice.mp3` / `voice.zip`** — розширення визначається по `Content-Type` відповіді (`application/zip` → `.zip`, інакше → `.mp3`). VoiceBot може повернути ZIP коли увімкнено `chunks` режим у шаблоні. Для Edge TTS завжди створюється `.mp3`.

- **VoiceBot polling:** `run_voiceover_sync` блокує потік `std::thread::sleep(5s)` між статусами. Для Edge TTS polling не потрібен — запит виконується синхронно за один виклик.

- **`template_uuid` для VoiceBot опціональний.** Якщо він порожній — задача TTS створюється без `template_uuid`. Валідація перед запуском вимагає лише `voicebot_key`.

- **Діалог назви задачі** (`egui::Window`) рендериться всередині `draw_pipeline_panel`. Авто-назва ("Задача N") рахує `jobs.len()` на момент натискання "Додати".

- **Виклик Claude CLI (`claude`) та Gemini CLI (`gemini`)**:
  Індивідуальні моделі для CLI зберігаються та валідуються окремо. При виклику Gemini CLI критично важливим є використання прапорців `--output-format json` (для отримання чистої відповіді без ANSI та службових рядків), `--yolo` (неінтерактивність) та `--skip-trust` (довіра воркспейсу). На Windows виклики проксуються через `cmd /C`.

- **Обмеження обсягу логу:** Глобальний логер тримає в пам'яті не більше 1000 записів, автоматично очищаючи старі для оптимізації споживання ОЗП.

- **Фонова валідація CLI-інструментів через `pending_tool_check`:** логіка відстежує зміну `translation_service` під час кожного `update()` та неблокуюче запускає перевірки `npm`, `gemini`, `claude`.

- **Зворотна сумісність параметрів Edge TTS (`clean_numeric_param`):** Для забезпечення сумісності зі старими шаблонами та файлами `settings.json`, які могли зберігати налаштування з декоративними суфіксами (наприклад, `+0%` чи `+0Hz`), функція `clean_numeric_param` в `src/gui/settings/storage.rs` автоматично очищає завантажені текстові поля під час виклику `load_settings` та `load_template`. Вона видаляє будь-які літери, відсотки чи герци на льоту, перетворюючи старі значення на чисті числові рядки, що запобігає збоям у роботі рушія синтезу.

- **Чітка обводка текстових полів у темних темах:** Для кращої видимості та естетичного сприйняття на темному та AMOLED фонах, у функцію `apply_theme` (`src/theme.rs`) додано примусове налаштування `widgets.inactive.bg_stroke = Stroke::new(1.0, Color32::from_gray(100))` для неактивних елементів керування. Це забезпечує тонку стильну обводку навколо всіх полів введення замість зливання з фоном.

- **Вирівнювання при переносі логу через `LayoutJob`**: Щоб уникнути зсувів та порожнеч при переносі довгих рядків логів на другу строчку, мітка часу та текст повідомлення об'єднуються в єдиний `egui::text::LayoutJob`. Рядок рендериться як один віджет `egui::Label` і переноситься цілісно під лівий край (під мітку часу), що забезпечує ідеальний вигляд терміналу.

## Локалізація

Всі UI-рядки — у `src/localization/{uk,en,ru}.rs`. Ключ додається у всі три файли одночасно. Якщо ключ відсутній — `translate()` повертає порожній рядок `""`.

Структура: `translate(language: Language, key: &str) -> &'static str`.
