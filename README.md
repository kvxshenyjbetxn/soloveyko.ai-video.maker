# Soloveyko.ai Video Maker

Десктопна програма для автоматизованого створення відео: переклад сценарію, озвучка, генерація відеоряду, субтитри та монтаж — все в одному пайплайні. Побудована на Rust + egui, кросплатформена (Windows / macOS).

---

## Архітектура

**Стек:** Rust + [eframe](https://github.com/emilk/egui/tree/master/crates/eframe) (egui). Один головний потік UI, всі мережеві запити або системні процеси (наприклад, виклики Claude CLI чи Gemini CLI) виконуються у окремих `std::thread::spawn` потоках та повертають результат через `Arc<Mutex<Option<T>>>` + `ctx.request_repaint()`. Для обмеження паралельних запитів до API OpenRouter, запусків Claude CLI та Gemini CLI використовуються потокобезпечні глобальні лімітери (семафори), що запобігають перевищенню лімітів та перевантаженню системи.

**State management:** Весь стан програми живе у єдиній структурі `VideoMakerApp` (`src/app.rs`). Немає глобальних змінних. Налаштування автоматично персистяться у JSON-файл при кожній зміні (але тільки коли миша відпущена — щоб не бомбардувати диск під час перетягування бічної панелі).

**Два режими відображення:** вкладка `Main` (редактор + панель пайплайну) та вкладка `Settings` (тема, мова, колір акценту).

**Розділення відповідальностей:**
- `api/` — тонкі обгортки для зовнішніх сервісів (перевірка балансу, ключів)
- `core/pipeline/` — бізнес-логіка кожного етапу пайплайну (HTTP виклик + збереження файлу + статус задачі)
- `gui/pipeline/` — тільки UI-компоненти панелі пайплайну

## Ключові компоненти

### `VideoMakerApp` (`src/app.rs`)

Центральна структура. Реалізує `eframe::App`, тобто метод `update()` — головний loop рендерингу.

- **Баланс-чіпи в топбарі та налаштування лімітів:** при кліку на будь-який чіп відкривається вікно `draw_balance_window`. Чіпи відображаються тільки якщо баланс вже завантажений (не `None`). VoiceBot показує лише перше слово балансу (числове значення), щоб не займати місце. У цьому ж вікні інтегровано повзунки `egui::Slider` (від 1 до 25) для регулювання `openrouter_max_threads`, `claude_max_threads` та `gemini_max_threads`. Будь-яка зміна цих повзунків миттєво оновлює відповідні глобальні лімітери запитів та автозберігається на диск.
- **Автозбереження:** в кінці `update()` порівнюється поточний стан з `last_saved_settings`. Якщо щось змінилось і миша відпущена (`!pointer.any_down()`) — файл перезаписується. Дельта для `translation_temperature`: > 0.001 (щоб уникнути зайвих записів під час перетягування повзунка).
- **Баланси завантажуються при старті:** якщо в налаштуваннях вже є ключі — виклик `fetch_balance` відбувається в `VideoMakerApp::new()`. OpenRouter перевіряється тільки якщо ключ починається з `sk-or-`.
- **Ширина панелі пайплайну:** egui зберігає ширину через `egui::Memory` між сесіями автоматично. `default_width` передається лише при першому запуску програми — далі егуі управляє шириною сам.
- **Нижня панель черги та ресайз:** `TopBottomPanel::bottom("queue_panel")` рендериться після правої бічної панелі пайплайну, тому вона візуально обмежується нею та не заходить під неї. Вона підтримує вертикальний ресайз `.resizable(true)` з межами висоти від 75px (мінімум) до 350px (максимум) з дефолтним значенням 90px. При збільшенні висоти картки адаптивно розширюються по вертикалі, показуючи більші іконки та деталі.
- **Клікабельність задач та вікно логів:** Кожна картка в черзі є інтерактивною (`Sense::click()`). При наведенні курсор змінюється на `PointingHand`. Клік по картці встановлює стан `selected_job_logs` та відкриває окреме спливаюче вікно `egui::Window` з детальними логами виключно цієї задачі.
- **`job_name_dialog_open` / `job_name_input`** — стан діалогового вікна назви задачі. Ephemeral, не зберігається у `settings.json`.

### Черга задач (`src/queue.rs`)

- **`JobSettings`** — знімок усіх налаштувань пайплайну на момент додавання задачі. Зберігається в `PipelineJob` для можливого майбутнього перезапуску. Поля озвучки: `voiceover_enabled`, `voicebot_key`, `voiceover_template_uuid`.
- **`JobStatus`** — `Pending → Running → Done / Failed(String)`. Обгорнутий у `Arc<Mutex<T>>`, бо змінюється з фонового потоку.
- **`StageStatus`** — `Pending / Running / Done / Failed` (без деталей помилки). Кожен `PipelineJob` має два окремих поля: `translation_stage` та `voiceover_stage`. Слугують виключно для UI: картка задачі фарбує назву кожного етапу відповідним кольором (сірий / жовтий / зелений / червоний).
- **`PipelineJob::name`** — назва задачі, яку вводить користувач у діалозі. Якщо поле пусте — автоматично генерується як "Задача N" (де N = `jobs.len() + 1` на момент додавання).
- **Двоетапний workflow:** додавання задачі (`Pending`) і запуск (`Running`) — два окремі дії. Користувач може накопичити кілька задач у черзі і потім запустити їх усі кнопкою "▶ Запустити".

### Панель пайплайну (`src/gui/pipeline/mod.rs`)

Права бічна панель з 8 секціями у порядку: Шаблони → Шлях збереження → АПІ → Переклад → Озвучка → Відеоряд → Субтитри → Монтаж.

- **Секції "Переклад", "Озвучка", "Відеоряд", "Субтитри", "Монтаж"** мають toggle-перемикач (`toggle_switch`) прямо в заголовку. Стан перемикача відображається плавною анімацією через `animate_bool_responsive`.
- **Кнопка швидкої вставки плейсхолдера `{{text}}`** у секції «Переклад» розміщена безпосередньо під текстовим полем промту. При натисканні вона вираховує поточний стан `egui::TextEditState`, знаходить char-індекс курсора та безпечно вставляє плейсхолдер у байтову UTF-8 позицію рядка без втрати фокусу, дозволяючи користувачеві миттєво продовжувати введення.
- **Форма шаблону** завжди видима поза `ScrollArea` — навмисно, щоб не ховалась при скролі. Кнопка "Додати в чергу" також зафіксована внизу панелі.
- **ScrollArea обмежена по висоті** (`max_height = available_height - bottom_reserve`) — щоб залишити місце для кнопки та помилки внизу.
- **Всі секції** реалізовані через `CollapsingState` з persist id — egui запам'ятовує чи розкрита секція між кадрами.
- **Кнопка "Додати в чергу":** спочатку валідує поля (текст, шлях, модель, ключ). Якщо все ок — відкриває `egui::Window` з полем для введення назви задачі. Вікно по центру екрана, підтримує `Enter` для підтвердження.
- **`validate_and_enqueue`** — більше НЕ запускає обробку. Тільки створює папку `{save_path}/{task_name}/` через `std::fs::create_dir_all` і додає `PipelineJob` зі статусом `Pending`. Реальний запуск — через кнопку "▶ Запустити" в панелі черги.

### Пайплайн виконання задачі (`src/core/pipeline/`)

**`run_pipeline`** (`mod.rs`) — єдина точка запуску задачі. Spawns один потік, виконує послідовно всі увімкнені етапи у межах цього потоку. Статус задачі: `Pending → Running → Done / Failed`.

#### Переклад (`translate/`)

- **`translate_text`** (`mod.rs`) — синхронна функція: будує `user_content` з промту + тексту, викликає відповідний сервіс. Повертає `Result<String>`. Не знає нічого про статуси, файли чи потоки.
- **`call_openrouter`** (`translate.rs`) — чистий HTTP виклик до OpenRouter Chat API.
- **Плейсхолдер `{{text}}`:** якщо промт містить `{{text}}` — текст підставляється на місце. Якщо промт є але без плейсхолдера — текст додається після промту через `\n\n`. Якщо промт порожній — надсилається тільки текст.
- При успіху зберігає результат у `{save_path}/text.txt`. Цей же текст передається в озвучку якщо вона увімкнена.

#### Озвучка (`voiceover/`)

**`run_voiceover_sync`** (`voiceover/voiceover.rs`) — синхронна функція, викликається з `run_pipeline` після перекладу (або замість нього, якщо переклад вимкнено).

Логіка:
1. `POST /tasks` — створює TTS задачу на VoiceBot сервері, отримує `task_id`.
2. Polling `GET /tasks/{id}/status` кожні 5 секунд. Кожен запит пише лог до задачі з поточним статусом.
3. При статусі `ending` або `ending_processed` — завантажує результат `GET /tasks/{id}/result`.
4. Зберігає файл у `{save_path}/voice.mp3` або `voice.zip` (визначається по `Content-Type` відповіді).
5. При статусі `error` або `error_handled` — повертає `Err`.

**Джерело тексту:** якщо переклад увімкнено — озвучується перекладений текст. Якщо переклад вимкнено — оригінальний текст (`settings.text`). Картка задачі показує це окремим рядком: "Переклад" (кольоровий за статусом) або "Оригінал" (завжди зелений, бо текст уже є).

### Вікно привітання (`src/gui/welcome.rs`)

З'являється при першому запуску (або якщо `show_welcome: true` у `settings.json`). Перевіряє наявність трьох CLI-інструментів асинхронно у фонових потоках, одразу при ініціалізації `VideoMakerApp::new()`.

- **`ToolStatus`** — три стани: `Checking` / `Installed(String)` / `NotInstalled`. Зберігається в `Arc<Mutex<ToolStatus>>`.
- **`ToolChecks::start()`** spawns три окремих `std::thread::spawn`. Кожен запускає відповідну команду (`npm --version`, `gemini --version`, `claude --version`) та оновлює статус після завершення через `ctx.request_repaint()`.
- **На Windows** перевірки запускаються через `cmd /C <name> --version` (аналогічно до `api/gemini.rs` та `api/claude.rs`).
- **Команди встановлення** показуються тільки якщо інструмент `NotInstalled`, залежать від OS: Mac — `brew install node` / `sudo npm install -g @google/gemini-cli`, Windows — `winget install OpenJS.NodeJS` / `npm install -g @google/gemini-cli`. Claude Code однаковий на всіх системах.
- **"Не показувати":** галочка `dont_show` + кнопка "Зрозуміло". `draw_welcome_dialog` повертає `true` лише коли кнопку натиснуто. Якщо `closed && dont_show` — `app.rs` миттєво зберігає `show_welcome: false` через явний виклик `save_settings` (не через автозбереження), щоб не гратися з `last_saved_settings`.

### Збереження налаштувань (`src/gui/settings/storage.rs`)

Два JSON-файли зберігаються у `<UserConfigDir>/Soloveyko.AI-Video.Maker/`:
- `settings.json` — `AppSettings`: весь стан програми (тема, ключі, ширина панелі, стан пайплайну тощо).
- `templates/<name>.json` — `PipelineTemplate`: набір налаштувань пайплайну для швидкого перемикання між конфігами.

`AppSettings` та `PipelineTemplate` мають `#[serde(default)]`, тому старі файли без нових полів не ламаються. Поле `show_welcome` має `default_true`, тому після оновлення на нову версію вікно привітання покаже себе один раз.

### API-сервіси (`src/api/`)

Тільки утилітарні запити (баланс, перевірка ключа). Всі запити — синхронні `ureq`, загорнуті в `std::thread::spawn`. Результат пишеться у `Arc<Mutex<Option<T>>>`, після чого `ctx.request_repaint()` ініціює перемальовування UI.

- **Глобальне лімітування запитів OpenRouter (`OpenRouterLimiter`), Claude Code (`ClaudeLimiter`) та Gemini CLI (`GeminiLimiter`):**
  Потокобезпечні лімітери (семафори на базі `Mutex` та `Condvar` зі стандартної бібліотеки Rust) обмежують кількість одночасних запитів до OpenRouter та паралельних запусків Claude CLI / Gemini CLI по всій програмі.
  - Метод `acquire()` блокує потік, якщо досягнуто ліміту активних запитів чи запусків, повертаючи відповідні дозволи (`OpenRouterPermit<'a>`, `ClaudePermit<'a>` або `GeminiPermit<'a>`).
  - Завдяки реалізації трейту `Drop` для дозволів, ліміт автоматично звільняється (викликається `release()`) при виході з області видимості, надійно запобігаючи витокам дозволів.
  - Лімітер OpenRouter інтегрований у перевірку балансу (`fetch_balance`), переклад сценарію (`call_openrouter`) та фонове завантаження моделей. Лімітер Claude Code інтегрований у функцію `call_claude_code`, а лімітер Gemini CLI — у функцію `call_gemini_cli` для обмеження паралельних процесів запуску CLI.

| Сервіс | Ендпоінт | Що повертає |
|---|---|---|
| **OpenRouter** | `openrouter.ai/api/v1/credits` | Залишок кредитів: `$X.XX` |
| **VoiceBot (баланс)** | `voiceapi.csv666.ru/balance` | `balance_text` — рядок з кількістю символів |
| **VoiceBot (TTS)** | `POST /tasks` → `GET /tasks/{id}/status` → `GET /tasks/{id}/result` | TTS workflow: створення задачі → polling статусу → скачування MP3/ZIP |
| **Googler** | `googler.fast-gen.ai/api/v3/account/usage` | `GooglerBalance`: img/video used+limit, threads active+allowed |

**VoiceBot TTS статуси:** `waiting` → `processing` → `ending` (скачуємо) → `ending_processed`. При `error` / `error_handled` — кошти повертаються на баланс автоматично. Ліміт: 5 одночасних задач.

**НО — Googler `account_limits`:** поля лімітів могут бути або числом, або об'єктом з ключем `used`/`count`/`current_usage`. Функція `extract_i64()` обробляє обидва формати, бо API Googler непостійний у структурі відповіді.

### Глобальний логер та Вкладка Логів (`src/logger.rs`)

Система надає преміальний вбудований термінал логів для діагностики виконання завдань (зокрема запусків Claude CLI та OpenRouter HTTP-запитів):
- **Потокобезпечний структурований логер:** реалізований на базі глобального `OnceLock<Mutex<Vec<LogEntry>>>` з обмеженням розміру до 1000 записів. Записує логи одночасно в інтерфейс додатку та в консоль розробника (`stdout`).
- **Прив'язка логів до задач:** Кожен запис `LogEntry` може містити `job_id` та `job_name`. Функція `log_job(job_id, job_name, msg)` записує лог із прив'язкою до задачі. У загальному списку такі логи автоматично маркуються префіксом `[Задача #ID: Назва]`.
- **Фільтрація логів:** Функція `get_job_logs(job_id)` дозволяє отримати логи тільки для конкретної задачі, що використовується у спливаючому вікні при кліку на картку задачі в черзі.
- **Часові мітки без важких залежностей:** для форматування часу `[HH:MM:SS]` використовується `std::time::SystemTime` та `UNIX_EPOCH` замість важкої сторонньої бібліотеки `chrono`.
- **Вкладка «Лог» (Logs):** відображається відразу після «Налаштування». Має стильний темно-вугільний вигляд з інтелектуальним підсвічуванням подій (червоний для помилок та stdout/stderr, зелений для успіхів, блакитний для команд, тьмяно-сірий для часу).
- **Керування логом:** кнопки «Очистити лог» (з червоним акцентом) та «Копіювати» для легкого копіювання всього логу в буфер обміну.

## API Інтеграції

| Сервіс | Призначення | Авторизація | Де налаштовується |
|---|---|---|---|
| **OpenRouter** | LLM-модель для перекладу сценарію | `Bearer sk-or-...` | Секція АПІ в пайплайні |
| **VoiceBot** | Озвучка тексту (TTS) + перевірка балансу | `X-API-Key` | Секція АПІ в пайплайні |
| **Googler** | Генерація зображень і відео | `X-API-Key` | Секція АПІ в пайплайні |
| **Claude Code** | Локальний AI-агент (через CLI `claude`) | Локальна авторизація в Claude CLI | Не потребує налаштування ключів у додатку |

Всі ключі зберігаються в `settings.json` у `UserConfigDir` (НЕ в репозиторії).

## Важливі нюанси та НО

- **Блокування на рівні `OpenRouterLimiter` не впливає на GUI-потік.** Оскільки всі мережеві виклики, які захищені лімітером (переклад сценарію, фонове завантаження моделей, перевірка балансу), виконуються у фонових потоках (`std::thread::spawn`), будь-яке блокування потоку семафором під час очікування вільного слоту відбувається непомітно для користувача і не спричиняє зависань інтерфейсу.

- **`googler_key` не входить у `PipelineTemplate`.** Ключ Googler зберігається тільки в `AppSettings` (глобальні налаштування), а не в шаблонах пайплайну. OpenRouter ключ — входить у шаблон. Така асиметрія є свідомою: шаблон — це конфіг пайплайну, а не конфіг акаунту.

- **`openrouter_max_threads`, `claude_max_threads` та `gemini_max_threads` не входять у `PipelineTemplate`.** Ці значення є системними лімітами потоків користувача і зберігаються в глобальних `AppSettings` (`settings.json`), а не в індивідуальних шаблонах пайплайну.

- **Баланс-чіп VoiceBot** показує лише перше слово (число) з `balance_text`, щоб не займати місце в топбарі. Повний текст видно у вікні балансів.

- **Googler-баланс у топбарі** відображає 8 значень в одному рядку (`img: X/Y vid: X/Y th: X/Y X/Y`). Це компромісне рішення — детальне вікно балансів показує те саме у читабельному вигляді (grid-таблиця).

- **`windows_subsystem = "windows"`** у `main.rs` — приховує консоль у release-білді на Windows. У debug-режимі консоль є.

- **egui перемальовує весь фрейм щоразу** — тому будь-яка зміна стану одразу видна. Немає event-системи: якщо значення змінилось до наступного `update()`, воно одразу відобразиться.

- **`translation_model_search`** — ephemeral-стан (рядок пошуку у дропдауні), не зберігається у `settings.json` та не входить у шаблон. Скидається при запуску.

- **Повзунок температури (`translation_temperature`)** — ширина Slider в egui не контролюється через `add_sized`, а лише через `ui.style_mut().spacing.slider_width`. Тому перед рендерингом зчитується `ui.available_width()` і встановлюється у `scope`, щоб не забруднювати стиль батьківського `ui`.

- **Ширина елементів у `ui.horizontal()`:** egui автоматично додає `item_spacing.x` між кожною парою елементів. При розрахунку ширини першого елемента треба відіймати саме `ui.spacing().item_spacing.x`, а не довільне число — інакше рядок виходить ширший за available і SidePanel розповзається.

- **Секції "Субтитри" та "Монтаж"** поки порожні (заглушки). Їх наявність у пайплайні — місце під майбутню функціональність.

- **Шлях збереження задачі** — не сам `save_path`, а `{save_path}/{task_name}/`. Папка створюється при додаванні задачі в чергу (в `validate_and_enqueue`), а не при запуску. Якщо `create_dir_all` падає — задача не додається, показується помилка.

- **Кольорова система статусів у картці задачі:** кожен увімкнений етап відображається окремим рядком і фарбується незалежно: сірий = очікує, жовтий = виконується, зелений = готово, червоний = помилка. "Оригінал" завжди зелений — він не потребує виконання. Загальний рядок статусу задачі (Очікує / Виконується / Готово / Помилка) відображається окремо під етапами.

- **Архітектура пайплайну — один потік на задачу.** Раніше `run_translation` spawning власний потік. Тепер `run_pipeline` spawns один потік і послідовно виконує всі увімкнені етапи. Це дозволяє легко додавати нові етапи і гарантує правильну послідовність (переклад → озвучка, а не паралельно). Статус `Running` — поки хоча б один етап активний.

- **Файл озвучки `voice.mp3` / `voice.zip`** — розширення визначається по `Content-Type` відповіді (`application/zip` → `.zip`, інакше → `.mp3`). Файл завжди називається `voice`, суфікс — з відповіді сервера. VoiceBot може повернути ZIP коли увімкнено `chunks` режим у шаблоні.

- **VoiceBot polling:** `run_voiceover_sync` блокує потік `std::thread::sleep(5s)` між запитами. Це не впливає на UI, бо виконується у фоновому потоці. Кожен запит статусу пише лог до задачі — видно у спливаючому вікні логів при кліку на картку.

- **`template_uuid` для VoiceBot опціональний.** Якщо `voiceover_template_uuid` порожній — задача TTS створюється без `template_uuid` (сервер використовує налаштування за замовчуванням). Тому валідація перед запуском вимагає лише `voicebot_key`, але не `template_uuid`.

- **Діалог назви задачі** (`egui::Window`) рендериться всередині `draw_pipeline_panel`, але egui::Window завжди малюється поверх усього контексту — не прив'язується до SidePanel. Авто-назва ("Задача N") рахує `jobs.len()` на момент натискання "Додати", тому якщо додати дві задачі одночасно і залишити обидві без назви — отримаємо "Задача 1" і "Задача 2" послідовно.

- **Виклик Claude CLI (`claude`) та прапорці:**
  Для інтеграції Claude Code використовується локальний бінарник `claude`. Запуск здійснюється за допомогою прапорців:
  - `--model <model>` — вибір моделі (`sonnet`, `opus`, `haiku`).
  - `-p <prompt>` — передача промпту.
  З міркувань сумісності, на Windows виклик здійснюється через `cmd.exe` з аргументами `/C claude`, тоді як на macOS та Linux команда запускається безпосередньо. При виборі сервісу Claude Code повзунок температури та налаштування OpenRouter приховуються, оскільки Claude CLI бере на себе управління сесією.

- **Виклик Gemini CLI (`gemini`) та прапорці:**
  Для інтеграції Google Gemini CLI використовується локальний бінарник `gemini`. Запуск здійснюється за допомогою прапорців:
  - `--model <model>` — вибір моделі (наприклад, `gemini-2.5-flash`, `gemini-2.5-pro` тощо).
  - `--output-format json` — повертає структурований JSON `{"session_id":"...","response":"текст","stats":{...}}`. Єдиний надійний спосіб отримати чисту відповідь: без `update_topic{...}` інлайн-викликів, ANSI-кодів та службових рядків, які CLI виводить у `text`-режимі.
  - `--prompt <prompt>` — передача промпту.
  - `--yolo` (або `--approval-mode yolo`) — критичний прапорець для неінтерактивного виконання, який автоматично погоджує всі пропоновані дії та інструменти.
  - `--skip-trust` — прапорець автоматичної довіри воркспейсу, необхідний для роботи в неінтерактивному фоновому режимі.
  З міркувань сумісності, на Windows виклик здійснюється через `cmd.exe` з аргументами `/C gemini`, тоді як на macOS та Linux команда запускається безпосередньо. При виборі сервісу Gemini CLI повзунок температури та налаштування OpenRouter приховуються.

- **`show_welcome` в автозбереженні:** поле збережено як `self.last_saved_settings.show_welcome` (без прив'язки до live-стану). Зміна `show_welcome: false` відбувається виключно через явний `save_settings` у блоці welcome-логіки в `update()`, не через загальний автозберігаючий блок внизу. Це уникає race condition: якщо б `show_welcome` потрапив у загальне порівняння, воно б ніколи не спрацьовувало (live-значення = `last_saved_settings.show_welcome` завжди рівні).

- **Маскування сценаріїв у логах:** З міркувань конфіденційності та чистих логів без засмічення інтерфейсу величезними текстами, реальний промпт сценарію у виклику команди замінюється в логах статичною заглушкою `"[текст промпту та сценарію]"`. На реальний запуск процесу це не впливає — туди передається оригінальний повний текст.

- **Обмеження обсягу логу:** Глобальний логер тримає в пам'яті не більше 1000 записів. При перевищенні ліміту найстаріші записи автоматично видаляються з пам'яті, захищаючи програму від надмірного споживання ОЗП при тривалій роботі.

## Локалізація

Всі UI-рядки — у `src/localization/{uk,en,ru}.rs`. Ключ додається у всі три файли одночасно. Якщо ключ відсутній — `translate()` повертає порожній рядок `""` (матч `_ => ""`).

Структура: `translate(language: Language, key: &str) -> &'static str`.
