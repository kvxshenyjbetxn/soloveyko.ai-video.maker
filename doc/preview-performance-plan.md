# План оптимізації превʼю в редакторі монтажу

Мета: зменшити навантаження на CPU, диск і GPU під час перегляду превʼю в редакторі, не змінюючи якість фінального FFmpeg/CapCut рендеру.

## Пріоритет реалізації

1. Обмежити зайві `request_repaint()`.
2. Зменшити розмір FFmpeg chunk-ів для preview-cache.
3. Додати єдину чергу preview extraction.
4. Додати Auto/Eco режим превʼю.
5. Додати proxy-відео для великих файлів.

## 1. Eco / Auto режим превʼю

Додати режим, який автоматично знижує навантаження при слабкому ПК або великому проєкті.

Ідея:

- автоматично перемикати превʼю на `Performance + 15 FPS`, якщо багато відеокліпів або UI починає лагати;
- знижувати активність, коли редактор не у фокусі або перекритий іншими вікнами;
- не впливати на фінальний рендер.

## 2. Обмеження `request_repaint()`

У `src/gui/montage_editor/preview.rs` є місця, де repaint може викликатися занадто часто.

Що зробити:

- під час очікування кадру використовувати `request_repaint_after(100-300ms)`;
- повний `request_repaint()` залишити для playback, drag, transition та активної підготовки кадру;
- не тримати CPU активним, якщо кадр ще не готовий і нічого не анімується.

## 3. Менші FFmpeg chunk-и для preview-cache

У `src/gui/montage_editor/frame_cache.rs` chunk під час playback може генерувати до 18 секунд кадрів. Для 30 FPS це сотні JPEG-файлів за один запуск.

Пропозиція:

- playback chunk: 3-6 секунд;
- scrub chunk: 1-3 секунди;
- prefetch переважно вперед від playhead;
- не генерувати великі ділянки, якщо користувач швидко перескочив в інше місце.

## 4. Єдина черга FFmpeg-завдань

Замість багатьох незалежних потоків для кадрів і chunk-ів зробити preview-worker з пріоритетами.

Пріоритети:

1. Поточний кадр під playhead.
2. Найближчі наступні кадри для playback.
3. Кадри для scrub fallback.
4. Sharp still кадр.

Обмеження:

- `Performance`: максимум 1 FFmpeg процес;
- `Balanced`: максимум 1-2 FFmpeg процеси;
- `High/Ultra`: максимум 2 процеси;
- застарілі задачі видаляти з черги.

## 5. Обережна генерація sharp-frame

Sharp still кадри покращують якість на паузі, але коштують дорожче.

Що змінити:

- генерувати sharp тільки для `High` та `Ultra`;
- запускати sharp після паузи 300-500 мс;
- не генерувати sharp під час playback, drag, transition або активного overlay;
- якщо scrub-кадр уже достатньо якісний, не запускати sharp повторно.

## 6. Proxy-відео для великих файлів

Для важких `.mp4`, `.mov`, `.mkv` створювати легкий proxy-файл для превʼю.

Приклад proxy:

- ширина 640-960 px;
- 15 FPS;
- низький bitrate;
- формат `.mp4` або послідовність JPEG/WebP кадрів.

Важливо:

- превʼю читає proxy;
- фінальний рендер завжди використовує оригінальний файл;
- proxy кешується у `.frame_cache` і перевикористовується між сесіями.

## 7. Оптимізація логіки `preview.rs`

У `src/gui/montage_editor/preview.rs` кожен repaint виконує пошук активних кліпів, сортування та підготовку overlay.

Можливі покращення:

- кешувати активні кліпи для поточного playhead;
- індексувати кліпи по доріжках;
- не сортувати весь список на кожному repaint;
- мінімізувати `clone()` великих структур у гарячому шляху.

## 8. Пауза превʼю, коли воно не потрібне

Якщо редактор згорнутий, перекритий Stock Picker або користувач не взаємодіє з превʼю:

- не запускати FFmpeg extraction;
- не підігрівати кадри;
- не генерувати sharp still;
- показувати останній доступний кадр.

## Очікуваний результат

Після впровадження цих змін має зменшитися:

- кількість одночасних FFmpeg процесів;
- навантаження на CPU;
- кількість записів JPEG на диск;
- частота repaint у egui;
- ривки під час playback і scrub.

Фінальна якість відео не має змінитися, бо всі оптимізації стосуються тільки preview-режиму редактора.
